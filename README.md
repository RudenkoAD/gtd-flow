# GTD Flow

Плагин Obsidian для GTD поверх обычных Markdown-задач: **входящие**, **kanban-доски**, **календарь**, **отложенный ящик** (tickler), **регулярные задачи** и **проекты-графы** с зависимостями.

## Идея

**Состояние выводится, а не хранится.** Источник истины — строки задач в ваших `.md`-файлах. Плагин строит по ним индекс, и каждый вид — просто проекция этого индекса на «сегодня»:

- отложенная задача (`🛫` в будущем) сама возвращается во входящие, когда дата наступает — **без единой записи в файл**;
- задача проекта всплывает во входящие, как только выполнены все её зависимости `⛔` — тоже чистым пересчётом;
- единственное, что плагин создаёт сам, — копии регулярных задач (идемпотентно: детерминированные `🆔`, дубли от двух устройств сталкиваются, а не размножаются).

Формат строк совместим с эмодзи-форматом плагина Tasks (`📅`, `🛫`, `🔁`, `🆔`, `⛔`…), но GTD Flow полностью самодостаточен: Tasks/Kanban/Dataview не требуются. Ваши файлы остаются обычным Markdown — плагин можно выключить в любой момент, данные никуда не денутся.

## Семь видов

| Вид | Что показывает |
|---|---|
| Входящие | неразобранный захват (файлы `gtd-inbox`) + готовые задачи проектов; обычные заметки — опционально (тумблер в настройках) |
| Доска (kanban) | активные задачи по колонкам (тег `#kanban/<доска>/<колонка>` или статус) |
| Календарь | задачи с датой (due → scheduled → start), drag = перенос даты; в почасовой сетке click-drag создаёт событие с длительностью; дни красятся статусами |
| Отложенные | задачи с `🛫` в будущем, бакеты «Скоро / Неделя / Позже» |
| Регулярные | шаблоны с `🔁` из файлов-каталогов, история копий, пауза/резюм, удаление |
| Проекты (обзор) | список проектов со статусом и прогрессом; клик по строке открывает граф |
| Проект (граф) | задачи файла-проекта как DAG: рёбра = `⛔`, готовые подсвечены |

Каждый вид — обычная вкладка Obsidian: сплиты, перетаскивание вкладок, pop-out окна работают из коробки. Карточки перетаскиваются между видами; на телефоне и между окнами — контекстное меню «Переместить в…» и команды палитры.

## Установка

Требуется Obsidian **1.7.2 или новее** (десктоп и мобильный). Плагин пока не в каталоге community plugins, поэтому ставится одним из трёх способов.

### Способ 1 — BRAT (рекомендуется: автообновления)

[BRAT](https://github.com/TfTHacker/obsidian42-brat) — плагин для установки бета-плагинов прямо из GitHub-релизов.

1. **Включите сторонние плагины:** Настройки → «Сторонние плагины» → кнопка «Включите плагины сообщества» (выход из ограниченного режима).
2. **Установите BRAT:** там же «Плагины сообщества → Обзор» → в поиске наберите `BRAT` → откройте карточку (автор TfTHacker) → «Установить» → «Включить».
3. **Добавьте GTD Flow:** Настройки → «Сторонние плагины» → шестерёнка у BRAT → кнопка **Add beta plugin** → в поле репозитория вставьте:

   ```
   RudenkoAD/gtd-flow
   ```

   Оставьте галку «Enable after installing the plugin» и нажмите **Add plugin**.
4. BRAT скачает последний релиз, установит и включит GTD Flow — в левой ленте появятся иконки видов, а в палитре команд (`Ctrl/Cmd+P`) — команды «Открыть: …». Обновления будут подтягиваться автоматически при запуске Obsidian.

### Способ 2 — вручную из релиза

1. Откройте [последний релиз](https://github.com/RudenkoAD/gtd-flow/releases/latest) и скачайте три файла: `main.js`, `manifest.json`, `styles.css`.
2. Создайте папку `<ваше хранилище>/.obsidian/plugins/gtd-flow/` и положите файлы туда.
3. Перезапустите Obsidian → Настройки → «Сторонние плагины» → включите **GTD Flow** (если список пуст — сначала выключите ограниченный режим, см. шаг 1 выше).

Обновление — повторить с файлами нового релиза.

### Способ 3 — из исходников (для разработки)

```bash
git clone https://github.com/RudenkoAD/gtd-flow
cd gtd-flow
npm i
npm run build   # соберёт main.js
```

Скопируйте `main.js`, `manifest.json`, `styles.css` в `<хранилище>/.obsidian/plugins/gtd-flow/` — либо сделайте симлинк/junction папки плагина на клон репозитория, тогда после каждой пересборки достаточно перезагрузить Obsidian (`Ctrl/Cmd+P` → «Перезагрузить приложение без сохранения»).

> **Первый запуск:** на хранилище без GTD-файлов плагин предложит создать демо-файлы — см. «Быстрый старт» ниже. Данные плагину не принадлежат: всё хранится обычными Markdown-строками в ваших заметках, отключение плагина ничего не ломает.

## Быстрый старт

При первом запуске на пустом хранилище GTD Flow показывает приветственный диалог: можно одной кнопкой создать демо-файлы (пример доски, проекта с зависимостями, регулярной задачи и события) и сразу открыть рабочее пространство, либо начать с чистого листа. Демо ничего не перезаписывает и создаётся только по вашему согласию — существующие заметки не затрагиваются. Пересоздать пример в любой момент можно командой палитры **«Создать демо-файлы GTD»**.

Если предпочитаете собрать всё вручную:

1. Создайте файл `GTD/Inbox.md` (путь настраивается) и накидайте задач:

   ```markdown
   - [ ] Позвонить в сервис по поводу машины
   - [ ] Продлить страховку ⏫ 📅 2026-07-20
   - [ ] Отложенная задача (уйдёт в «Отложенные») 🛫 2026-09-01
   ```

2. Выполните команду **«Открыть рабочее пространство GTD»** — откроются Входящие, Доска и Отложенные. Любой вид открывается и отдельной командой «Открыть: …».

3. Доска — файл с frontmatter `gtd-board: true`:

   ```markdown
   ---
   gtd-board: true
   id: work
   name: Работа
   group-by: tag
   columns:
     - { id: todo, name: "К работе", match: "#kanban/work/todo" }
     - { id: doing, name: "В работе", match: "#kanban/work/doing" }
     - { id: done, name: "Готово", match: "#kanban/work/done" }
   ---
   - [ ] Ревью PR по интеграции #kanban/work/todo
   - [/] Миграция базы на новую схему #kanban/work/doing
   - [x] Настроить CI #kanban/work/done ✅ 2026-07-10
   ```

   Колонки — только теги `#kanban/<доска>/<колонка>`; со статусом «готово/не готово» они никак не связаны. Карточку любого статуса можно перетащить в любую колонку (выполненные и отменённые показываются зачёркнутыми). Готовую карточку из контекстного меню доски можно **Архивировать** — она уходит со всех досок, а её строка переносится в `archiveFile` (по умолчанию `GTD/Archive.md`).

4. Проект — файл с `gtd-project: true`; зависимости — `⛔` на `🆔` других задач файла:

   ```markdown
   ---
   gtd-project: true
   name: Ремонт кухни
   status: active
   ---
   - [x] Обмерить кухню 🆔 k7f2a1 ✅ 2026-07-10
   - [ ] Собрать сметы подрядчиков 🆔 m3q9z4 ⛔ k7f2a1
   - [ ] Заказать материалы 🆔 r2t5v9 ⛔ m3q9z4
   ```

   «Собрать сметы» уже во входящих (зависимость выполнена), «Заказать материалы» ждёт своей очереди.

5. Регулярные — файл с `gtd-recurring: true`; все задачи в нём — шаблоны:

   ```markdown
   ---
   gtd-recurring: true
   ---
   - [ ] Еженедельное ревью #review 🔁 every week on friday 🆔 rev-week
   - [ ] Ревью приоритетов 🔺 🔁 every month on the last day 🛫 -3d 🆔 rev-prio
   ```

   В нужный день копия появляется во входящих; курсор `🔜` на шаблоне сдвигается автоматически. Правила: `every day`, `every 2 weeks on mon, thu`, `every month on the 31st` (в феврале — 28/29), `every year on april 1 until 2027-01-01`. Границы серии задают `from …` (нижняя, включительно) и `until …` (верхняя): `every wednesday from 2026-07-15 until 2026-09-10`.

   **`every!` — повтор «от выполнения»** (как в Todoist): следующее вхождение отсчитывается от **даты, когда вы отметили `✅` предыдущую копию**, а не по календарной сетке. Новая копия появляется только после того, как предыдущая выполнена, — просроченные не накапливаются пачкой. Примеры:

   ```markdown
   - [ ] Полить цветы 🔁 every! 3 days 🆔 flowers
   - [ ] Поменять фильтр 🔁 every! month 🆔 filter
   ```

   Выполнили полив 15-го — следующая копия запланируется на 18-е (`✅ + 3 дня`); выполнили с опозданием 20-го — на 23-е. Допустимо для любой частоты (`every! 2 weeks`, `every! year`), совместимо с `from …`/`until …`, но **несовместимо с `on …`/днём недели** (`every! week on tue` бессмысленно — от выполнения нет фиксированного дня); у `every! month`/`every! year` день/дату указывать не нужно — он берётся от даты выполнения. Только для задач: у **событий** календаря `every!` запрещён (событие не «выполняется»).

   Переезд с плагина **Tasks** без переписывания строк: суффикс `when done` (`🔁 every 3 weeks when done`) читается как алиас `every!` — та же семантика «от выполнения». Писать можно любым из двух вариантов; каноническая запись — `every!`. Дата из перенесённой строки Tasks (`📅`/`🛫`/`⏳`) в копии не дублируется — они остаются недатированными, как у обычного шаблона; а будущая дата просто откладывает первую копию до своего наступления.

6. Входящие — файл с `gtd-inbox: true`:

   ```markdown
   ---
   gtd-inbox: true
   ---
   - [ ] Позвонить в сервис по поводу машины
   ```

   Флаг помечает файл как **цель быстрого ввода** и как источник входящих. Новые задачи из поля во «Входящих», quick-add календаря и команды «Быстрый ввод» дописываются в первый (по имени) помеченный файл активного пространства; если ни один файл не помечен — берётся конвенционный фолбэк `<Корневая папка Общего>/Входящие.md` (для именованного пространства — `<корень>/Входящие.md`), который сам создаётся и помечается `gtd-inbox: true`. **По умолчанию** во «Входящие» попадают только активные неразобранные задачи из таких файлов `gtd-inbox` и готовые задачи проектов — задачи из обычных заметок не учитываются, чтобы чек-листы со всего хранилища не затапливали входящие. Чтобы вернуть старое поведение (входящие смотрят на весь vault), включите тумблер **«Входящие: включать задачи из обычных заметок»** в настройках. Как и раньше, разобранная задача из входящих уходит: получила `📅`/`🛫`, тег доски `#kanban/…` или зависимость `⛔` — исчезла из входящих чистым пересчётом.

7. Архив — файл с `gtd-archive: true`:

   ```markdown
   ---
   gtd-archive: true
   ---
   - [x] Настроить CI 🆔 21jnie ✅ 2026-07-10
   ```

   Полностью инертный контейнер: его задачи не попадают **ни в один** вид — ни во входящие, ни на доску, ни в календарь, ни в отложенные. Архив «замораживает» строки: снятие галочки у заархивированной задачи больше не возвращает её во входящие. Пункт меню доски **Архивировать** сам создаёт файл (по умолчанию `GTD/Archive.md`), проставляет этот флаг и переносит туда строку.

Готовый пример хранилища создаёт приветственный диалог первого запуска (или команда «Создать демо-файлы GTD»); большое синтетическое — `node scripts/gen-test-vault.mjs <папка>`.

## Формат полей

| Эмодзи | Поле |
|---|---|
| `📅` | due — срок; опционально время и интервал: `📅 2026-07-25 14:30-16:00` |
| `⏳` | scheduled — запланировано (время поддерживается так же) |
| `🛫` | start — отложено до даты (tickler) |
| `➕` | created — дата создания |
| `✅` | done — дата выполнения |
| `❌` | cancelled — дата отмены |
| `🔁` | правило повторения: шаблоны в `gtd-recurring` и серии событий в `gtd-events` (`every tuesday at 19:00-20:30`) |
| `🔺 ⏫ 🔼 🔽 ⏬` | приоритет: от наивысшего к низшему |
| `🆔` | идентификатор задачи |
| `⛔` | зависимости — список `🆔` через запятую |
| `🔜` | *своё поле:* курсор следующего вхождения шаблона |
| `🧬` | *своё поле:* ссылка копии на `🆔` шаблона; у одноразового события — на `🆔` серии |
| `🚫` | *своё поле:* даты-исключения серии событий (перенесённые/отменённые вхождения), список через запятую |
| `📍` | *своё поле:* место/адрес — свободный текст; у событий календаря показывается подсказкой под названием при наведении |

Статусы: `[ ]` активна, `[/]` в работе, `[x]` выполнена, `[-]` отменена (у шаблона — пауза). Тег `#waiting` — «жду ответа».

## Настройки (кратко)

- **commonRoot** — «Корневая папка „Общего“»: дом для файлов, создаваемых в пространстве «Общее» (быстрый ввод «Общего» → `<commonRoot>/Входящие.md`, доски, проекты — по конвенции от неё), default `GTD`. Это папка ДЛЯ СОЗДАНИЯ, а не признак принадлежности — файл вне корней пространств относится к «Общему» независимо от того, где лежит. Заменила прежнюю настройку `inboxSources`;
- **inboxIncludePlain** — включать ли во «Входящие» задачи из обычных заметок (default `false` — входящие смотрят только на файлы `gtd-inbox` и проекты; `true` — на весь vault);
- **calendarPlacement** — приоритет даты для календаря (due → scheduled → start);
- **deferPresets** — кнопки быстрого откладывания («Завтра», «+3 дня»…);
- **promoteTo** — куда возвращается отложенная задача: остаться на месте или во входящие;
- **recurring** — файл-приёмник копий и политика догона после перерыва (`latest` — одна свежая копия, `all`, `none`);
- **cardsFolder** — папка заметок-карточек («Открыть карточку» создаёт заметку с приватным чеклистом);
- **dayStatusFile** — файл статусов дней (default `GTD/DayStatus.md`; при нетронутом дефолте следует за `commonRoot`), см. ниже;
- **namespaces** — несколько независимых GTD в одном хранилище (по умолчанию пусто — всё как раньше), см. раздел ниже;
- дебаунсы, порог виртуализации, первый день недели, авто-вставка `🆔`.

## Статусы дней (покраска календаря)

Календарь красит дни по статусам из файла с флагом `gtd-day-status: true`. Статусы и цвета задаются в frontmatter, назначения — строками тела (побеждает последняя подходящая):

```markdown
---
gtd-day-status: true
statuses:
  работаю: "#4c8bf5"
  учусь: "#9c27b0"
  в командировке: "#e5892a"
  выходной: "#4caf50"
---
2026-07-20: работаю
2026-08-01..2026-08-10: в командировке
every week on saturday,sunday: выходной
```

Форматы назначения: одиночная дата, диапазон `дата..дата`, правило повторения (та же грамматика, что у `🔁`). Красить можно и из UI календаря: клик по полосе-статусу дня выбирает статус, протяжка по полосам шапок — диапазон (как многодневное событие). Файл при первой покраске создаётся автоматически со стартовой палитрой.

## Пространства (несколько GTD в одном хранилище)

Иногда в одном хранилище нужны **несколько независимых GTD** — например «Работа» и «Личное», — чтобы входящие, доски, календарь, отложенные, проекты и регулярные одной жизни не смешивались с другой. Для этого есть **пространства** (namespaces).

**Пространство = папка.** В настройках (**«Пространства GTD» → «Список пространств»**) задаётся список «Имя: корневая/папка», по одному на строку:

```
Работа: Areas/Work
Личное: Areas/Personal
```

Дальше всё работает само:

- **Принадлежность файла** — по самому длинному совпавшему корню-префиксу пути: `Areas/Work/Проект.md` и `Areas/Work/Клиенты/Acme.md` — оба в «Работе» (вложенность любой глубины). Вложенные пространства допустимы: при наличии и `Areas/Work`, и `Areas/Work/Клиенты` файл из второй папки достаётся более длинному корню.
- **«Общее»** — всё, что вне заданных корней. Это встроенное пространство: пока список пуст, существует только оно, и плагин ведёт себя ровно как раньше (обратная совместимость — включать ничего не нужно).
- **Frontmatter `gtd-namespace: Имя`** перебивает папку — для файла-исключения, который физически лежит вне своей папки, но логически относится к пространству.

**Переключение — пофайловое (per-view):** у каждой вкладки вида — **своё** активное пространство. Компактный **селектор в шапке вида** (появляется, только когда настроено ≥1 пространство) меняет только этот вид; данные вкладки фильтруются её пространством. Новая вкладка наследует **глобальный дефолт** (он же — цель быстрого ввода из палитры). Команда палитры **«Переключить пространство GTD»** переключает всё разом: глобальный дефолт и локальные пространства всех открытых вкладок. Пикеры меню («Переместить в колонку…», «В проект…») показывают доски/проекты **пространства самой задачи** (перенос идёт внутри её пространства, а не активного вида). **Статусы дней — общие** для всех пространств (календарь всех «жизней» красится одинаково).

**Общие события видны везде; вкладка «Все».** Серии-события пространства **«Общее»** (файлы вне папок пространств) показываются в календаре **любого** пространства — общий праздничный/семейный календарь не нужно дублировать по «жизням». Это касается только событий: задачи «Общего» в чужой календарь не протекают. У календаря есть дополнительная опция переключателя **«Все»** — она сводит задачи и события **всех** пространств сразу в один вид; быстрый ввод в режиме «Все» уходит в глобальный дефолт (с уведомлением, в какое пространство добавлено).

**Куда создаются новые файлы.** «Общее» встаёт в один ряд с именованными: его конвенционные файлы создаются под **«Корневой папкой Общего»** (`commonRoot`, default `GTD`) — быстрый ввод «Общего» уходит в `<commonRoot>/Входящие.md` (ровно как именованное — в `<корень>/Входящие.md`). Часть целей «Общего» пока берётся из выделенных настроек (`eventsFile`, `archiveFile`, файл копий регулярных `recurring.spawnTarget`) — они по умолчанию тоже лежат под `GTD`. Для именованного пространства всё создаётся по конвенции от его корня:

| Что создаётся | Путь (именованное пространство) |
|---|---|
| Быстрый ввод; фолбэк копий регулярных | `<корень>/Входящие.md` |
| События календаря | `<корень>/События.md` |
| Архив | `<корень>/Архив.md` |
| Новая доска | `<корень>/Доски/<имя>.md` |
| Новый проект | `<корень>/Проекты/<имя>.md` |
| Шаблоны регулярных | первый файл `gtd-recurring` внутри пространства, иначе `<корень>/Регулярные.md` |

Копия регулярной задачи всегда попадает во входящие **пространства шаблона** (а не активного): рабочий шаблон спавнит в рабочие входящие, даже когда активно «Личное».

## MCP-сервер (агенты в вашей GTD)

В комплекте идёт автономный **MCP-сервер** (`mcp-server.js`) — он даёт агентам (Claude Code, Claude Desktop) читать и править вашу GTD **напрямую по файлам хранилища**, без запущенного Obsidian. Так можно попросить агента «разбери входящие», «что у меня на этой неделе», «заведи задачу», «перенеси карточку в Готово» — и он сделает это теми же правилами, что и плагин (тот же парсер полей-эмодзи, адресация задач по 🆔/content-key, конвенции пространств).

Сервер переиспользует чистое ядро плагина и пишет через атомарный read-modify-write (temp-файл + rename). **Все операции заперты внутри корня хранилища; файлы не удаляются** (delete_task убирает только строку задачи). Индекс строится полным сканом хранилища на каждый вызов инструмента — всегда согласован с диском после ваших правок в Obsidian. Конфигурация (пространства, `commonRoot`, `eventsFile` и пр.) читается из `<vault>/.obsidian/plugins/gtd-flow/data.json`, если он есть, иначе берутся дефолты.

**Инструменты:**

| Инструмент | Что делает |
|---|---|
| `gtd_overview` | Пространства (имя, корень) и счётчики: входящие / отложенные / доски / проекты / события. |
| `list_tasks` | Задачи с фильтрами `namespace`, `view` (`inbox`/`tickler`/`board`/`project`/`all`), `board`, `project`, `include_done`. |
| `add_task` | Новая задача во «Входящие» пространства (текст может содержать поля-эмодзи; опц. `due`/`scheduled`/`start`). |
| `update_task` | Правка по id (🆔 или content-key): `done`, `text`, даты (строка — задать, `null` — снять), `priority`, `location` (📍: строка — задать, `null`/пустая — снять). |
| `delete_task` | Удалить строку задачи (по умолчанию вместе с вложенным блоком). |
| `move_card` | Перенести карточку в колонку доски (в конец колонки). |
| `list_events` | Развёрнутые вхождения календаря в диапазоне `from`..`to` (серии + одноразовые, с местом 📍). |
| `add_event` | Событие в файл событий пространства: одноразовое (`date` + опц. `time`) или серия (`rule` по грамматике повторов), опц. `location`. |
| `list_boards` | Доски пространства с колонками и числом карточек. |

Аргумент `namespace` принимает имя пространства (`Работа`), `Общее` или `all`; если опущен — активное пространство из настроек.

### Сборка

```bash
npm run build:mcp     # → mcp-server.js (один файл, esbuild). Входит и в `npm run build`.
```

### Подключение в Claude Code

```bash
claude mcp add gtd -- node "D:\путь\к\плагину\mcp-server.js" --vault "D:\путь\к\vault"
```

(Путь к хранилищу можно задать и через переменную окружения `GTD_VAULT` вместо `--vault`.)

### Подключение в Claude Desktop

В `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "gtd": {
      "command": "node",
      "args": ["D:\\путь\\к\\плагину\\mcp-server.js", "--vault", "D:\\путь\\к\\vault"]
    }
  }
}
```

> ⚠️ **Сервер пишет в файлы вашего хранилища напрямую.** Это те же правки, что делает плагин, но их инициирует агент — держите хранилище под контролем версий (git) или бэкапом, если доверяете агенту редактирование. Сервер никогда не удаляет файлы и не выходит за пределы указанного корня.

## Разработка

```bash
npm i
npm run dev        # esbuild watch → main.js
npm test           # проверка чистоты core + vitest (1300+ тестов)
npm run build      # typecheck + production-сборка
```

Архитектура: `src/core/` — чистый TypeScript без единого импорта `obsidian` (парсер, индекс, запросы, движки повторов и DAG; контролируется `scripts/check-core-purity.mjs`), `src/adapters/` — тонкий клей к API Obsidian, `src/views/` — Svelte 5 (граф — Svelte Flow). `src/mcp/` — автономный MCP-сервер (см. раздел выше): переиспользует ядро и сервисы с fs-портами вместо адаптеров Obsidian, той же проверкой чистоты запрещён импорт `obsidian`.

## Ограничения

- **Нет фоновых уведомлений и напоминаний.** Плагин живёт внутри Obsidian: пока приложение закрыто, ничего не срабатывает. Это не баг, а честная граница платформы — «возврат» отложенных и спавн регулярных происходят сравнением дат при старте и раз в минуту, поэтому закрытые периоды безопасны (всё догоняется при первом открытии). Если однажды понадобятся push-напоминания на телефоне, повторы «когда ни одно устройство не открыто», виджеты или дистрибуция вне Obsidian — это зафиксированный триггер для переезда ядра в отдельное приложение: core плагина написан без зависимостей от Obsidian именно на этот случай.
- Рисование рёбер графа — только на десктопе (на мобильных — режим списка).
- Кросс-видовой drag на телефоне выключен (single pane) — используйте меню «Переместить в…» и команды палитры; это полноценный, а не запасной интерфейс.
