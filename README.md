# GTD Flow

Плагин Obsidian для GTD поверх обычных Markdown-задач: **входящие**, **kanban-доски**, **календарь**, **отложенный ящик** (tickler), **регулярные задачи** и **проекты-графы** с зависимостями.

> **0.14.0 / Android core + desktop AI.** GTD Flow now uses one configurable
> inbox and explicit task scopes instead of runtime namespaces. Inbox, Calendar,
> task editing and Recurring are supported in Obsidian for Android; the embedded AI,
> OAuth, graph/DnD and the remaining views stay available only in Obsidian Desktop.
> Existing namespace vaults can be migrated on desktop
> through the built-in dry-run workflow; see [Migration from namespaces](#migration-from-namespaces)
> and the [breaking AI Inbox MVP release notes](docs/BREAKING_AI_INBOX_MVP.md).

## Идея

**Состояние выводится, а не хранится.** Источник истины — строки задач в ваших `.md`-файлах. Плагин строит по ним индекс, и каждый вид — просто проекция этого индекса на «сегодня»:

- отложенная задача (`🛫` в будущем) сама возвращается во входящие, когда дата наступает — **без единой записи в файл**;
- задача проекта всплывает во входящие, как только выполнены все её зависимости `⛔` — тоже чистым пересчётом;
- единственное, что плагин создаёт сам, — копии регулярных задач (идемпотентно: детерминированные `🆔`, дубли от двух устройств сталкиваются, а не размножаются).

Формат строк совместим с эмодзи-форматом плагина Tasks (`📅`, `🛫`, `🔁`, `🆔`, `⛔`…), но GTD Flow полностью самодостаточен: Tasks/Kanban/Dataview не требуются. Ваши файлы остаются обычным Markdown — плагин можно выключить в любой момент, данные никуда не денутся.

## Виды

| Вид             | Что показывает                                                                                                                                      |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Входящие        | неразобранный захват из одного настроенного файла + готовые задачи проектов; обычные заметки — опционально (тумблер в настройках)                   |
| Доска (kanban)  | активные задачи по колонкам (тег `#kanban/<доска>/<колонка>` или статус)                                                                            |
| Календарь       | задачи с датой (due → scheduled → start), drag = перенос даты; в почасовой сетке click-drag создаёт событие с длительностью; дни красятся статусами |
| Отложенные      | задачи с `🛫` в будущем, бакеты «Скоро / Неделя / Позже»                                                                                            |
| Регулярные      | шаблоны с `🔁` из файлов-каталогов, история копий, пауза/резюм, удаление                                                                            |
| Проекты (обзор) | список проектов со статусом и прогрессом; клик по строке открывает граф                                                                             |
| Проект (граф)   | задачи файла-проекта как DAG: рёбра = `⛔`, готовые подсвечены                                                                                      |
| GTD AI          | desktop chat и разговоры запусков; OpenRouter подключается и работает только по явному действию пользователя                                        |

На Android регистрируются только виды **Входящие**, **Календарь** и
**Регулярные**; общий редактор задачи доступен из поддержанных карточек.

Каждый вид — обычная вкладка Obsidian: сплиты, перетаскивание вкладок и pop-out
окна работают из коробки. Между отдельными окнами используйте контекстное меню
«Переместить в…» и команды палитры.

### Редактирование задачи

Во **Входящих**, на **доске** и в **Отложенных** обычный клик по области карточки
вне названия и встроенных кнопок открывает полный редактор задачи. Двойной клик
по самому названию по-прежнему запускает быстрое inline-переименование; checkbox,
меню, ссылки и индикатор чеклиста выполняют собственные действия и не открывают
редактор. Перетаскивание карточки также не вызывает диалог после drop.

В полном редакторе доступны название, выполнение, приоритет, `📅`/`⏳`/`🛫` с
опциональным временем или интервалом, `📍`, длительность, три интенсивности и
scope. Кнопка **«Сохранить»** применяет все изменённые поля одной атомарной
правкой целевой строки, поэтому строка не остаётся с частично применённым набором
полей. Если у задачи ещё нет стабильного `🆔`, он может быть добавлен перед этой
правкой для безопасной записи истории обучения. Системный контекст (файл,
заголовок, ID, повторение и зависимости) показывается отдельно; задача из внешнего
read-only календаря открывается только для просмотра.

Ручная правка или очистка любого из полей `⏱`/`🧠`/`💓`/`💪`/`🧭` делает именно
это поле пользовательским и блокирует дальнейшую AI-перезапись. Остальные
AI-поля сохраняют своё прежнее владение; вернуть поле AI можно только явной
командой разблокировки и переоценки.

Скриншоты будут добавлены после стабилизации нового UI; README не ссылается на
неопубликованные placeholder-файлы.

## Установка

Требуется Obsidian **1.7.2 или новее**. Manifest универсальный
(`isDesktopOnly: false`): на Android поддержаны Входящие, Календарь, редактор
задачи и Регулярные. Desktop сохраняет полный набор видов, AI/OpenRouter,
внешнюю синхронизацию, DnD и pop-out. iOS пока не входит в проверенную матрицу.
Плагин пока не в каталоге community plugins, поэтому ставится одним из трёх способов.

### Способ 1 — BRAT (рекомендуется: автообновления)

[BRAT](https://github.com/TfTHacker/obsidian42-brat) — плагин для установки бета-плагинов прямо из GitHub-релизов.

1. **Включите сторонние плагины:** Настройки → «Сторонние плагины» → кнопка «Включите плагины сообщества» (выход из ограниченного режима).
2. **Установите BRAT:** там же «Плагины сообщества → Обзор» → в поиске наберите `BRAT` → откройте карточку (автор TfTHacker) → «Установить» → «Включить».
3. **Добавьте GTD Flow:** Настройки → «Сторонние плагины» → шестерёнка у BRAT → кнопка **Add beta plugin** → в поле репозитория вставьте:

   ```
   RudenkoAD/gtd-flow
   ```

   Оставьте галку «Enable after installing the plugin» и нажмите **Add plugin**.

4. BRAT скачает последний релиз, установит и включит GTD Flow — в левой ленте появятся иконки видов, а в палитре команд (`Ctrl/Cmd+P`) — команды «Открыть: …». Обновления будут подтягиваться автоматически при запуске Obsidian.

### Способ 2 — вручную из релиза

1. Откройте [последний релиз](https://github.com/RudenkoAD/gtd-flow/releases/latest) и скачайте три файла: `main.js`, `manifest.json`, `styles.css`.
2. Создайте папку `<ваше хранилище>/.obsidian/plugins/gtd-flow/` и положите файлы туда.
3. Перезапустите Obsidian → Настройки → «Сторонние плагины» → включите **GTD Flow** (если список пуст — сначала выключите ограниченный режим, см. шаг 1 выше).

Обновление — повторить с файлами нового релиза.

`mcp-server.js` и `widget-core.js` также публикуются в релизе, но не входят в папку
Obsidian-плагина: первый нужен только для MCP-интеграции, второй — для внешних
QuickJS/Android-виджетов. Целостность файлов можно проверить по `SHA256SUMS`.

### Способ 3 — из исходников (для разработки)

```bash
git clone https://github.com/RudenkoAD/gtd-flow
cd gtd-flow
npm i
npm run build   # соберёт main.js
```

Скопируйте `main.js`, `manifest.json`, `styles.css` в `<хранилище>/.obsidian/plugins/gtd-flow/` — либо сделайте симлинк/junction папки плагина на клон репозитория, тогда после каждой пересборки достаточно перезагрузить Obsidian (`Ctrl/Cmd+P` → «Перезагрузить приложение без сохранения»).

> **Первый запуск на desktop:** на хранилище без GTD-файлов плагин предложит создать демо-файлы — см. «Быстрый старт» ниже. На Android онбординг не создаёт файлы автоматически: откройте существующий синхронизированный vault или настройте Inbox/Scopes вручную. Данные плагину не принадлежат: всё хранится обычными Markdown-строками в ваших заметках, отключение плагина ничего не ломает.

## Быстрый старт

При первом запуске на пустом хранилище GTD Flow показывает приветственный диалог: можно одной кнопкой создать демо-файлы (пример доски, проекта с зависимостями, регулярной задачи и события) и сразу открыть рабочее пространство, либо начать с чистого листа. Демо ничего не перезаписывает и создаётся только по вашему согласию — существующие заметки не затрагиваются. Пересоздать пример в любой момент можно командой палитры **«Создать демо-файлы GTD»**.

Если предпочитаете собрать всё вручную:

1. Создайте файл `GTD/Inbox.md` (путь настраивается) и накидайте задач:

   ```markdown
   - [ ] Позвонить в сервис по поводу машины
   - [ ] Продлить страховку ⏫ 📅 2026-07-20
   - [ ] Отложенная задача (уйдёт в «Отложенные») 🛫 2026-09-01
   ```

2. Выполните команду **«Открыть рабочее пространство GTD»** — откроются Входящие, Доска и Отложенные. Любой вид открывается и отдельной командой «Открыть: …».

3. Доска — файл с frontmatter `gtd-board: true`:

   ```markdown
   ---
   gtd-board: true
   id: work
   name: Работа
   group-by: tag
   columns:
     - { id: todo, name: "К работе", match: "#kanban/work/todo" }
     - { id: doing, name: "В работе", match: "#kanban/work/doing" }
     - { id: done, name: "Готово", match: "#kanban/work/done" }
   ---

   - [ ] Ревью PR по интеграции #kanban/work/todo
   - [/] Миграция базы на новую схему #kanban/work/doing
   - [x] Настроить CI #kanban/work/done ✅ 2026-07-10
   ```

   Колонки — только теги `#kanban/<доска>/<колонка>`; со статусом «готово/не готово» они никак не связаны. Карточку любого статуса можно перетащить в любую колонку (выполненные и отменённые показываются зачёркнутыми). Готовую карточку из контекстного меню доски можно **Архивировать** — она уходит со всех досок, а её строка переносится в `archiveFile` (по умолчанию `GTD/Archive.md`).

4. Проект — файл с `gtd-project: true`; зависимости — `⛔` на `🆔` других задач файла:

   ```markdown
   ---
   gtd-project: true
   name: Ремонт кухни
   status: active
   ---

   - [x] Обмерить кухню 🆔 k7f2a1 ✅ 2026-07-10
   - [ ] Собрать сметы подрядчиков 🆔 m3q9z4 ⛔ k7f2a1
   - [ ] Заказать материалы 🆔 r2t5v9 ⛔ m3q9z4
   ```

   «Собрать сметы» уже во входящих (зависимость выполнена), «Заказать материалы» ждёт своей очереди.

5. Регулярные — файл с `gtd-recurring: true`; все задачи в нём — шаблоны:

   ```markdown
   ---
   gtd-recurring: true
   ---

   - [ ] Еженедельное ревью #review 🔁 every week on friday 🆔 rev-week
   - [ ] Ревью приоритетов 🔺 🔁 every month on the last day 🛫 -3d 🆔 rev-prio
   ```

   В нужный день копия появляется во входящих; курсор `🔜` на шаблоне сдвигается автоматически. Правила: `every day`, `every 2 weeks on mon, thu`, `every month on the 31st` (в феврале — 28/29), `every year on april 1 until 2027-01-01`. Границы серии задают `from …` (нижняя, включительно) и `until …` (верхняя): `every wednesday from 2026-07-15 until 2026-09-10`.

   **`every!` — повтор «от выполнения»** (как в Todoist): следующее вхождение отсчитывается от **даты, когда вы отметили `✅` предыдущую копию**, а не по календарной сетке. Новая копия появляется только после того, как предыдущая выполнена, — просроченные не накапливаются пачкой. Примеры:

   ```markdown
   - [ ] Полить цветы 🔁 every! 3 days 🆔 flowers
   - [ ] Поменять фильтр 🔁 every! month 🆔 filter
   ```

   Выполнили полив 15-го — следующая копия запланируется на 18-е (`✅ + 3 дня`); выполнили с опозданием 20-го — на 23-е. Допустимо для любой частоты (`every! 2 weeks`, `every! year`), совместимо с `from …`/`until …`, но **несовместимо с `on …`/днём недели** (`every! week on tue` бессмысленно — от выполнения нет фиксированного дня); у `every! month`/`every! year` день/дату указывать не нужно — он берётся от даты выполнения. Только для задач: у **событий** календаря `every!` запрещён (событие не «выполняется»).

   Переезд с плагина **Tasks** без переписывания строк: суффикс `when done` (`🔁 every 3 weeks when done`) читается как алиас `every!` — та же семантика «от выполнения». Писать можно любым из двух вариантов; каноническая запись — `every!`. Дата из перенесённой строки Tasks (`📅`/`🛫`/`⏳`) в копии не дублируется — они остаются недатированными, как у обычного шаблона; а будущая дата просто откладывает первую копию до своего наступления.

6. Входящие — один файл, выбранный в **«Настройки → Входящие → Файл
   входящих»** (по умолчанию `GTD/Inbox.md`):

   ```markdown
   ---
   gtd-inbox: true
   ---

   - [ ] Позвонить в сервис по поводу машины
   ```

   **Все** quick capture, экземпляры регулярных задач и возврат из tickler
   пишутся только в этот путь. При первой записи файл при необходимости создаётся
   и получает `gtd-inbox: true`. Этот frontmatter-флаг сохранён как
   compatibility-метаданные для старых vault, но больше не обнаруживает
   дополнительные источники: другой файл с `gtd-inbox: true` не становится
   входящими. **По умолчанию** вид показывает активные неразобранные задачи из
   настроенного файла и готовые задачи проектов. Задачи из обычных заметок не
   учитываются, чтобы чек-листы со всего vault не затапливали входящие; включить
   их можно тумблером **«Входящие: включать задачи из обычных заметок»**.
   Разобранная задача исчезает из входящих чистым пересчётом: получила
   `📅`/`🛫`, тег доски `#kanban/…` или зависимость `⛔`.

   **Быстрый ввод понимает даты.** Поле быстрого ввода (во «Входящих» и в колонках доски по кнопке «＋ Задача») распознаёт русские даты в начале или конце строки и само проставляет `📅` (при необходимости — время). Во время набора под полем видна подсказка вроде «📅 чт 15 авг · 15:00». Примеры:

   - `завтра в 15 позвонить маме` → «позвонить маме» с `📅 <завтра> 15:00`;
   - `через 3 дня сдать отчёт` → `📅` на три дня вперёд;
   - `в пятницу релиз` → ближайшая будущая пятница;
   - `15 августа отпуск` → ближайшее 15 августа (уже прошло в этом году — берётся следующий);
   - `с 14 до 16 совещание` → сегодня, интервал `14:00–16:00`.

   Понимаются «сегодня/завтра/послезавтра», «через N дней/недель», дни недели («в понедельник», «в следующий вторник»), «DD месяца» и «DD.MM[.ГГГГ]», время «в 15», «в 9 утра/вечера» и интервал «с 14 до 16». Распознаётся только выражение **в начале или конце** строки — в середине («спланировать завтра поездку») дата не трогается, а голое число без разделителя (`15`) датой не считается. В числовой форме без года месяц пишется **двумя цифрами** (`15.08`, `5.08`): иначе «обновить до 1.2», «прочитать главу 3.4» и «оплатить счёт 12.5» теряли бы набранное число, приняв его за дату. Не нужно распознавание — возьмите слово в кавычки: `"завтра"` → кавычки снимаются, дата не ставится.

7. Архив — файл с `gtd-archive: true`:

   ```markdown
   ---
   gtd-archive: true
   ---

   - [x] Настроить CI 🆔 21jnie ✅ 2026-07-10
   ```

   Полностью инертный контейнер: его задачи не попадают **ни в один** вид — ни во входящие, ни на доску, ни в календарь, ни в отложенные. Архив «замораживает» строки: снятие галочки у заархивированной задачи больше не возвращает её во входящие. Пункт меню доски **Архивировать** сам создаёт файл (по умолчанию `GTD/Archive.md`), проставляет этот флаг и переносит туда строку.

Готовый пример хранилища создаёт приветственный диалог первого запуска (или команда
«Создать демо-файлы GTD»). Большое синтетическое хранилище создаётся только в **новой**
папке: `node scripts/gen-test-vault.mjs <новая-папка>`. Генератор отказывается трогать
существующую папку; `--force` разрешён только для ранее созданного им vault с маркером
`.gtd-flow-test-vault` и заранее выводит список перезаписываемых файлов.

## Формат полей

| Эмодзи           | Поле                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| `📅`             | due — срок; опционально время и интервал: `📅 2026-07-25 14:30-16:00`                                               |
| `⏳`             | scheduled — запланировано (время поддерживается так же)                                                             |
| `🛫`             | start — отложено до даты (tickler)                                                                                  |
| `➕`             | created — дата создания                                                                                             |
| `✅`             | done — дата выполнения                                                                                              |
| `❌`             | cancelled — дата отмены                                                                                             |
| `🔁`             | правило повторения: шаблоны в `gtd-recurring` и серии событий в `gtd-events` (`every tuesday at 19:00-20:30`)       |
| `🔺 ⏫ 🔼 🔽 ⏬` | приоритет: от наивысшего к низшему                                                                                  |
| `🆔`             | идентификатор задачи                                                                                                |
| `⛔`             | зависимости — список `🆔` через запятую                                                                             |
| `🔜`             | _своё поле:_ курсор следующего вхождения шаблона                                                                    |
| `🧬`             | _своё поле:_ ссылка копии на `🆔` шаблона; у одноразового события — на `🆔` серии                                   |
| `🚫`             | _своё поле:_ даты-исключения серии событий (перенесённые/отменённые вхождения), список через запятую                |
| `📍`             | _своё поле:_ место/адрес — свободный текст; у событий календаря показывается подсказкой под названием при наведении |
| `⏱`              | **общая прошедшая длительность**: шаг 5m до 24h, затем только целые сутки; например `⏱ 90m` или `⏱ 2880m`           |
| `🧠`             | когнитивная интенсивность `0`–`5`                                                                                   |
| `💓`             | эмоциональная интенсивность `0`–`5`                                                                                 |
| `💪`             | физическая интенсивность `0`–`5` (именно телесное усилие)                                                           |
| `🧭`             | стабильный ID scope, например `🧭 work`                                                                             |

Статусы: `[ ]` активна, `[/]` в работе, `[x]` выполнена, `[-]` отменена (у шаблона — пауза). Тег `#waiting` — «жду ответа».

## Оценки, scope и настройки

Пример полностью размеченной задачи:

```markdown
- [ ] Reconcile invoices ⏱ 90m 🧠 4 💓 2 💪 0 🧭 work
```

`⏱` хранит **общее прошедшее время**, не только активную работу. Минимум — `5m`;
`0m` недопустимо. До `24h` используются шаги по пять минут. Начиная с `24h`,
принимаются только точные целые сутки: `1440m`, `2880m` и т. д.; `37h`
отклоняется, а не округляется. `90m` показывается как `1h 30m`, `1440m` как
`1d`, `2880m` как `2d`. Отсутствие поля означает «неизвестно».

Каждая интенсивность независима: `0` — неприменимо, `5` — максимум. Успешная
AI-оценка задаёт все три; у старой или ещё не обработанной задачи они могут
отсутствовать. `🧭` хранит ID, а не название scope: название можно переименовать,
не переписывая задачи.

Главные настройки:

- **Входящие → Файл входящих** — один Markdown-путь для capture, регулярных
  экземпляров и возврата отложенных задач;
- **Scopes** — создание, переименование, порядок, архивирование и безопасное
  удаление scope. Каталог синхронизируется в `.gtd-flow/config/scopes.json`;
- **AI и оценки** — явное включение AI, необязательный строгий ZDR и
  memory-only хранение OAuth-ключа;
- **Входящие: включать задачи из обычных заметок** — по умолчанию выключено;
- календарное размещение, пресеты отложения, повторы, карточки, доски и внешние
  календари остаются отдельными настройками.

### AI на desktop

AI не делает сетевых запросов при запуске и не обрабатывает Markdown-изменения
автоматически. Сначала создайте хотя бы один активный scope, включите AI, затем
нажмите **«Подключить»** в разделе **AI и оценки** или откройте вид **GTD AI**.
Маршрутизация по умолчанию следует политике вашего аккаунта OpenRouter, а ключ
всегда хранится только в памяти процесса.

Оценщик всегда выбирает лучший из уже настроенных активных scope и не создаёт
новые. Экземпляр регулярной задачи наследует текущие `⏱`/`🧠`/`💓`/`💪`/`🧭`
поля шаблона.

Подключение использует OpenRouter OAuth с PKCE/S256 и временный loopback callback;
все запросы идут только через `openrouter/free`, без платного fallback. Политики:

- **Политика аккаунта OpenRouter** — выбранное по умолчанию поведение;
- **Требовать Zero Data Retention** — fail-closed: если для бесплатного маршрута
  нет совместимого провайдера, запрос не будет отправлен.

Ключ существует только в памяти процесса: он не записывается в vault,
`.gtd-flow/`, `data.json`, логи или экспорт. После перезапуска Obsidian нужно
подключиться снова. «Отключить» очищает локальный ключ; удалённое отзывование
OAuth-ключа самим приложением OpenRouter не поддерживает.

Команды палитры:

- **Обработать входящие с AI**;
- **Отменить активную AI-обработку входящих**;
- **Переоценить задачу под курсором с AI**;
- **Разблокировать AI-поле задачи под курсором…**;
- **Открыть разговор последнего AI-запуска**;
- **Повторить ожидающие AI-запуски**.

Обработка и повтор запускаются только по этим явным действиям. Пользовательская
правка поля блокирует его от следующих AI-изменений, пока поле не будет явно
разблокировано и переоценено.

Ответ на уточняющий вопрос только сохраняет контекст в vault и сам по себе не
отправляет запрос. Контекст применяется к связанным AI-полям следующей явной
командой **«Переоценить задачу под курсором с AI»**.

Ожидание из-за настоящего ограничения частоты/квоты (`rate_limited`, например
HTTP 429) показывается отдельно от другой временной ошибки провайдера
(`retry_waiting`). Ни один из этих запусков не повторяется в фоне: повтор
остаётся явной командой.

Раздел **AI и оценки → История обучения** показывает до 50 последних событий и
текущее владение каждым полем задачи, экспортирует полную историю в JSON и
очищает её только после подтверждения. Встроенный просмотр намеренно скрывает
текст задач/вопросов, пути и данные провайдера; полный локальный экспорт нужен
для углублённой диагностики.

В обычном чате чтение заметок и GTD-данных выполняется без подтверждения.
Одиночные обратимые изменения задач, дат, статуса, приоритета, места, проектов и
досок показывают действие **Undo**. Удаление задачи или файла, bulk-операции и
необратимые изменения проекта/доски сначала показывают preview и выполняются
только после явного подтверждения. `.gtd-flow/`, `.obsidian/`, shell и прямой
доступ к файловой системе модели недоступны.

### Synced data and local secrets

Markdown остаётся источником текущих значений. Дополнительная синхронизируемая
история находится в vault:

```text
.gtd-flow/
  config/scopes.json
  ai/sessions/<session-id>/header.json
  ai/sessions/<session-id>/messages/<message-id>.json
  ai/runs/<run-id>.json
  ai/recovery-leases/<run-id>/<lease-id>.json
  ai/feedback/<event-id>.json
  ai/feedback-outbox/<event-id>.json
  ai/migrations/<migration-id>.json
```

Immutable session messages, runs, recovery leases, feedback, prepared feedback
records, scope catalog and migration journals are synced. Legacy
`ai/sessions/<session-id>.jsonl` files remain readable. Local plugin settings in
`.obsidian/plugins/gtd-flow/data.json` contain configuration choices such as the
inbox path and privacy policy, but never OAuth credentials. Credentials are
memory-only; local indexes and retry timers are rebuildable implementation state,
not synced records.

## Статусы дней (покраска календаря)

Календарь красит дни по статусам из файла с флагом `gtd-day-status: true`. Статусы и цвета задаются в frontmatter, назначения — строками тела (побеждает последняя подходящая):

```markdown
---
gtd-day-status: true
statuses:
  работаю: "#4c8bf5"
  учусь: "#9c27b0"
  в командировке: "#e5892a"
  выходной: "#4caf50"
---

2026-07-20: работаю
2026-08-01..2026-08-10: в командировке
every week on saturday,sunday: выходной
```

Форматы назначения: одиночная дата, диапазон `дата..дата`, правило повторения (та же грамматика, что у `🔁`). Красить можно и из UI календаря: клик по полосе-статусу дня выбирает статус, протяжка по полосам шапок — диапазон (как многодневное событие). Файл при первой покраске создаётся автоматически со стартовой палитрой.

## Внешние календари (ICS)

Подписки на **iCal-ленты** (`.ics`) — секретный адрес Google Calendar, published-ссылка Outlook, ссылка `webcal://` кнопки «Подписаться», любой публичный `.ics`-URL — материализуются в файлы-зеркала и появляются в календаре, агенде и виджетах как обычные события. Настраиваются в **«Настройки → Внешние календари»**: имя, адрес и интервал опроса (по умолчанию 5 мин). `webcal://` автоматически заменяется на `https://`; суффикс `-<id>` в имени файла разводит одноимённые подписки по разным зеркалам.

- **Секретный адрес Google:** Google Календарь → настройки нужного календаря → раздел «Интеграция календаря» → «Секретный адрес в формате iCal».
- **Только для чтения.** Зеркало перезаписывается синхронизацией — правки в файле затрутся; в календаре внешние события помечены 🔗, а их меню предлагает лишь «Копировать…» (создаёт ваше одноразовое событие в обычном файле) и «Открыть файл».
- **Окно развёртки:** 14 дней назад и 92 вперёд от сегодня (повторы, EXDATE, переносы-исключения и таймзоны разворачиваются через `ical.js`; времена приводятся к локальной зоне устройства).
- **Идемпотентность:** одна и та же лента даёт байт-в-байт одинаковый файл, поэтому зеркало спокойно синхронизируется между устройствами (Remotely Save / Obsidian Sync) без ложных конфликтов; запись происходит только при реальном изменении ленты.
- **Приватность.** Секретный ICS-адрес — это доступ к вашему календарю на чтение; он хранится локально в `data.json` хранилища, относитесь к нему как к паролю.

## Migration from namespaces

Runtime namespace routing is removed. Views, capture and discovery are global;
scope is an explicit `🧭 <scope-id>` field on a task, not a folder filter.
`gtd-namespace` frontmatter and legacy namespace settings are read only by the
one-time migration wizard and are not interpreted during normal operation.

Before migrating, create at least one active scope and set the target **Файл
входящих**. Run **«Мигрировать пространства в scope…»**. The wizard requires an
explicit choice for the legacy coverage (only old inbox tasks or every task) and
for former Common tasks (leave unscoped or map to a selected scope), then maps
each named namespace to an active scope.

1. **Dry-run** lists every required `🆔` insertion, `🧭` annotation and inbox-block
   move and writes nothing.
2. **Подтвердить и применить** creates an immutable before-image journal in
   `.gtd-flow/ai/migrations/<migration-id>.json`, inserts only the IDs selected
   by that plan, applies its annotations and moves active inbox blocks to the
   unified inbox. ID insertion is part of the journaled operation, so rollback
   restores the exact pre-ID Markdown.
3. A crash or write conflict leaves the journal inspectable. Use
   **«Продолжить миграцию пространств…»** with its ID to retry idempotently, or
   **«Откатить миграцию пространств…»** to restore the captured files and previous
   inbox setting. Neither action guesses over a file changed outside the plan.

Keep a vault backup until the journal reports completion. The migration is the
only compatibility path; do not add new runtime `namespace` configuration,
selectors or `gtd-namespace` metadata.

## MCP-сервер (агенты в вашей GTD)

В GitHub-релиз входит автономный **MCP-сервер** (`mcp-server.js`) — он даёт агентам
(Claude Code, Claude Desktop) читать и править вашу GTD **напрямую по файлам
хранилища**, без запущенного Obsidian. Для ручной установки скачайте
`mcp-server.js` отдельно из того же релиза. Так можно попросить агента «разбери
входящие», «что у меня на этой неделе», «заведи задачу», «перенеси карточку в
Готово» — и он сделает это теми же правилами, что и плагин (тот же парсер
полей-эмодзи, адресация задач по 🆔/content-key, unified inbox и scope).

Сервер переиспользует чистое ядро плагина. Он делает лёгкий metadata-обход хранилища и переиспользует неизменившиеся содержимое и индекс; поэтому внешние правки Obsidian всё равно подхватываются, а каждый вызов не перечитывает весь vault. **Все операции заперты внутри корня хранилища; файлы не удаляются** (delete_task убирает только строку задачи). Мутации сериализуются по каноническому пути и перед атомарной заменой проверяют актуальность содержимого; при внешнем конфликте операция повторяется или возвращает ошибку, а не ложный успех. Конфигурация unified inbox и отображения читается из `<vault>/.obsidian/plugins/gtd-flow/data.json`, а scope catalog — из синхронизируемого `<vault>/.gtd-flow/config/scopes.json`. Отсутствующий `data.json` использует дефолты, но битый или недоступный файл блокирует write-инструменты, а не перенаправляет запись в `GTD/`.

**Инструменты:**

| Инструмент     | Что делает                                                                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gtd_overview` | Глобальные счётчики и синхронизируемый каталог scope.                                                                                                             |
| `list_tasks`   | Глобальные задачи с фильтрами `scope`, `view` (`inbox`/`tickler`/`board`/`project`/`all`), `board`, `project`, `include_done`.                                    |
| `add_task`     | Новая задача в configured unified inbox; принимает `duration_minutes`, три intensity-поля и `scope`, а также даты.                                                |
| `update_task`  | Правка по id (🆔 или content-key), включая `duration_minutes`, `cognitive_intensity`, `emotional_intensity`, `physical_intensity` и `scope`; `null` очищает поле. |
| `delete_task`  | Удалить строку задачи (по умолчанию вместе с вложенным блоком).                                                                                                   |
| `move_card`    | Перенести карточку в колонку доски (в конец колонки).                                                                                                             |
| `list_events`  | Развёрнутые вхождения календаря в диапазоне `from`..`to` (серии + одноразовые, с местом 📍).                                                                      |
| `add_event`    | Событие в configured events file: одноразовое (`date` + опц. `time`) или серия (`rule` по грамматике повторов), опц. `location`.                                  |
| `list_boards`  | Все доски с колонками и числом карточек.                                                                                                                          |

Это breaking MCP contract: `namespace` больше не существует ни во входах, ни в
выходах. Используйте `scope` со стабильным ID. Чтение может фильтровать и
архивированный известный scope; создание и обновление принимают только активный
scope.

### Widget core v2

Внешний QuickJS/Android bundle `widget-core.js` также больше не знает namespaces.
`computeWidgetData` принимает необязательный `inboxScope` (стабильный ID) и
возвращает каталог `scopes`; metadata каждой задачи содержит `durationMinutes`,
`durationLabel`, три intensity-поля, `scopeId` и `scopeName`. `buildEditedLine`
принимает camelCase поля `durationMinutes`, `cognitiveIntensity`,
`emotionalIntensity`, `physicalIntensity` и `scopeId` для ручной правки. Виджет
не выполняет OAuth/AI-запросов и остаётся работоспособным без AI-состояния.

Для навигации из внешнего Android-виджета плагин регистрирует узкий Obsidian URI
contract. Имя vault и все значения query должны быть URL-encoded:

- `obsidian://gtd-flow?vault=<vault>&view=inbox` открывает единые Входящие;
- `obsidian://gtd-flow?vault=<vault>&view=calendar&mode=day&date=YYYY-MM-DD`
  открывает календарь в режиме одного дня на указанной реальной дате.

Неизвестные виды, режимы и невалидные даты отклоняются без изменения workspace.

## Разработка

```bash
npm i
npm run dev        # esbuild watch → main.js
npm test           # проверка архитектурных границ + Vitest
npm run build      # typecheck + три production-бандла
npm run verify     # lint/format/Svelte/coverage/browser/build/release — как в CI
```

Перед первым browser-прогоном установите закреплённый Chromium:
`npx playwright install chromium`. Полный gate поддерживается на Node `>=20.19.0`;
CI проверяет минимальную версию `20.19.0` и актуальную ветку Node 22.

Регрессия инкрементального скана большого хранилища идёт на 3 000 заметок: этого
достаточно для проверки счётчиков ввода-вывода и хватает бюджета даже на
медленном диске. Полномасштабный замер — `GTD_PERF_NOTES=10000 npx vitest run
src/mcp/fsVault.test.ts`.

Архитектура: `src/core/` — чистый TypeScript без единого импорта `obsidian` (парсер, индекс, запросы, движки повторов и DAG; контролируется `scripts/check-core-purity.mjs`), `src/adapters/` — тонкий клей к API Obsidian, `src/views/` — Svelte 5 (граф — Svelte Flow). `src/mcp/` — автономный MCP-сервер (см. раздел выше): переиспользует ядро и сервисы с fs-портами вместо адаптеров Obsidian, той же проверкой чистоты запрещён импорт `obsidian`.

## Ограничения

- Android MVP поддерживает только **Входящие, Календарь, редактор задачи и
  Регулярные**. AI/OpenRouter/OAuth, проекты, доски, tickler, карточки, DnD,
  onboarding, фоновая iCal-синхронизация и возврат отложенных задач остаются
  desktop-only. Их `node:http`/`electron`-зависимости подключаются только за
  ленивой desktop-границей; собранный bundle проверяет
  `scripts/check-packaged-plugin.mjs`. iOS в этом релизе не тестируется и не
  заявляется поддержанным.
- **Нет фоновых уведомлений и напоминаний.** Плагин живёт внутри Obsidian: пока
  приложение закрыто, ничего не срабатывает. Регулярные задачи используют
  детерминированные ID (включая миграцию старых шаблонов без `🆔`) и догоняются
  при следующем открытии Obsidian; дубли после синхронизации Android и desktop
  запускают автоматический проход схождения, без ожидания следующего дня.
- `widget-core.js` остаётся отдельным QuickJS-артефактом для Android widgets;
  сами widgets открывают mobile views через `obsidian://gtd-flow`.
- Рисование рёбер графа, OAuth loopback callback и AI processing требуют desktop
  runtime; AI на мобильных не поддерживается.
